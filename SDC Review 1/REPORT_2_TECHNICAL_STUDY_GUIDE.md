# PART B — DOCUMENT PROCESSING PIPELINE

```
PDF File  ──►  PyMuPDF (Text Extraction)  ──►  Cleaning Regex  ──►  Section Detection
                                                                       │
ChromaDB Vector Store  ◄──  BGE Embedding  ◄──  Semantic Chunking  ◄───┘
```

### Stage-by-Stage Breakdown

#### 1. PyMuPDF Layout Extraction
* **Why:** Raw PDFs encode text visually, scattering multi-column text blocks. PyMuPDF (`fitz`) extracts text sorted by reading order ($Y$ and $X$ coordinates).
* **Input:** Raw binary PDF document stream.
* **Output:** Formatted text string containing uncleaned document pages.
* **Example:** Extracts text from page 3, preserving two-column paragraph ordering.

#### 2. Cleaning & Formatting Normalization
* **Why:** Running headers, footers, page numbers, and hyphenated line breaks (`trans- \n former`) distort embedding semantics.
* **Input:** Raw uncleaned text string.
* **Output:** Cleaned continuous text block.
* **Example:** `trans- \n former` $\rightarrow$ `transformer`.

#### 3. Section-Aware Detection
* **Why:** Scientific papers follow structural sections (`Abstract`, `Introduction`, `Methodology`, `Results`, `Conclusion`). Tracking sections enables section-scoped filtering.
* **Input:** Cleaned text block.
* **Output:** Text blocks assigned structural section metadata tags.

#### 4. LlamaIndex Semantic Sliding-Window Chunking
* **Why:** Passing an entire 10-page paper to an embedding model causes context overflow. Fixed-character splitting breaks sentences midway. Semantic chunking splits text into 512-token windows with 64-token overlaps.
* **Input:** Section-tagged text blocks.
* **Output:** Array of 512-token chunk objects with 64-token overlap between adjacent chunks.

#### 5. BGE Dense Embedding Generation
* **Why:** Converts textual chunks into 768-dimensional numerical vectors for fast spatial similarity search.
* **Input:** 512-token chunk text string.
* **Output:** 768-dimensional float vector array `[-0.024, 0.081, ..., 0.012]`.

#### 6. Dual Index Storage (ChromaDB + PostgreSQL)
* **Why:** Vectors require fast approximate nearest-neighbor indexing (ChromaDB), while document metadata (author, title, DOI, year) requires relational SQL querying.
* **Output:** Vectors stored in ChromaDB; metadata records inserted into SQLite/PostgreSQL.

# PART C — DENSE EMBEDDINGS (`BAAI/bge-base-en-v1.5`)

### 1. What is an Embedding?
* **Simple English:** A way of turning a piece of text into a list of numbers (a coordinate point in high-dimensional space) so that words with similar meanings end up close to each other.
* **Technical Explanation:** `[General Technical Explanation]` A continuous dense vector representation $\vec{v} \in \mathbb{R}^d$ mapped from discrete text tokens through a transformer encoder. The spatial distance (e.g., Cosine similarity) between two vectors reflects their semantic similarity:
  $$\text{Cosine Similarity}(\vec{u}, \vec{v}) = \frac{\vec{u} \cdot \vec{v}}{\|\vec{u}\| \|\vec{v}\|}$$
* **ResearchMind Example:** `[Project Fact]` We use `BAAI/bge-base-en-v1.5` which encodes text chunks into $d = 768$ dimensions. ChromaDB indexes 14,850 chunk vectors in our local KB.

---

### 2. "What happens if keyword search fails but semantic search succeeds?"
* **Scenario:** A researcher queries *"heart muscle inflammation"*.
* **Keyword Search (BM25):** Fails to find exact matches if the paper only uses the medical term *"myocarditis"*.
* **Semantic Search (BGE Dense Embedding):** Converts both terms into vector space. Because `bge-base-en-v1.5` was trained on scientific text, the vector for *"heart muscle inflammation"* resides near the vector for *"myocarditis"* (Cosine similarity $> 0.85$). Semantic search successfully retrieves the paper.

# PART D — BM25 LEXICAL RETRIEVAL

### 1. Mathematical Mechanics of BM25
`[General Technical Explanation]` BM25 (Best Matching 25) is a probabilistic rank function scoring relevance based on term frequency ($TF$), inverse document frequency ($IDF$), and document length normalization:

$$\text{Score}_{\text{BM25}}(D, Q) = \sum_{i=1}^{n} \text{IDF}(t_i) \cdot \frac{f(t_i, D) \cdot (k_1 + 1)}{f(t_i, D) + k_1 \cdot \left(1 - b + b \cdot \frac{|D|}{\text{avgdl}}\right)}$$

Where:
* $f(t_i, D)$: Frequency of query term $t_i$ in document $D$.
* $\text{IDF}(t_i) = \ln \left( \frac{N - n(t_i) + 0.5}{n(t_i) + 0.5} + 1 \right)$: Inverse document frequency weighting rare terms higher.
* $k_1 = 1.5$: Controls term frequency saturation (prevents repetitive keywords from over-inflating scores).
* $b = 0.75$: Controls document length normalization penalty.

---

### 2. Why BM25 is Crucial for Scientific Literature
* **Simple English:** Scientific papers contain exact acronyms (e.g., `"ResNet-50"`, `"ds_nexus_v10"`, `"r_m(d)"`), chemical symbols, or author names that dense embeddings can compress and lose. BM25 guarantees exact keyword hits are never lost.
* **Strengths:** Ultra-fast (P50 = 8.4 ms), parameter-free, perfect exact-string matching.
* **Limitations:** Misses synonyms, insensitive to word order or semantic context.

# PART E — DENSE RETRIEVAL MECHANICS

```
Query Text  ──►  BGE Encoder  ──►  Query Vector (768-dim)  ──►  ChromaDB HNSW Search  ──►  Top-20 Vectors
```

### 1. Vector Search Execution
1. Query string $q$ is passed to `BAAI/bge-base-en-v1.5`, producing vector $\vec{v}_q \in \mathbb{R}^{768}$.
2. ChromaDB executes an Approximate Nearest Neighbor (ANN) search using HNSW (Hierarchical Navigable Small World) indexing.
3. Computes vector distances across 14,850 stored chunk vectors, returning the top-20 nearest candidate document chunks ($R_{\text{dense}}$).

### 2. Comparative Example: BM25 vs Dense Retrieval Behavior
* **Query:** *"Deep learning for crop plant health"*
* **BM25 Behavior:** Matches chunks containing the exact words `"deep"`, `"learning"`, `"crop"`, `"plant"`. Fails if paper uses `"neural networks"` and `"agricultural disease"`.
* **Dense Retrieval Behavior:** Retrieves snippet `"Convolutional networks for agricultural disease detection"` because vector embeddings map plant health and agricultural disease to adjacent coordinates.

# PART F & G — HYBRID RETRIEVAL & RECIPROCAL RANK FUSION (RRF $k=60$)

## 1. Why We Need Hybrid Retrieval
`[Project Fact]` Pure dense retrieval misses specific acronyms; pure BM25 misses semantic synonyms. Combining them via hybrid retrieval bridges both gaps. In E01, hybrid search improved MRR to **0.812** ($+0.162$ over dense-only, $p=0.0002$).

---

## 2. Mathematical Deep Dive into RRF

### RRF Formula
$$S_{\text{RRF}}(d \in R) = \sum_{m \in \{\text{sparse}, \text{dense}\}} \frac{1}{k + r_m(d)}$$

Where:
* $r_m(d)$: 1-based rank position of document $d$ in retriever $m$.
* $k = 60$: Rank smoothing parameter.

### Role of $k = 60$
The parameter $k$ smooths rank decay. A small $k$ (e.g., $k=1$) penalizes lower ranks exponentially ($\frac{1}{1+1} = 0.5$ vs $\frac{1}{1+10} = 0.09$), allowing top-ranked outliers to dominate. Setting $k=60$ balances rank contributions ($\frac{1}{61} = 0.01639$ vs $\frac{1}{70} = 0.01428$), ensuring documents that perform consistently well across *both* retrievers rank highest.

---

## 3. Step-by-Step RRF Calculation Example

Assume 4 documents evaluated across BM25 and Dense Retrieval:

| Document ID | BM25 Rank ($r_{\text{sparse}}$) | Dense Rank ($r_{\text{dense}}$) | RRF Computation | Final RRF Score | Final Fused Rank |
| :---: | :---: | :---: | :--- | :---: | :---: |
| **Doc A** | 1 | 2 | $\frac{1}{60+1} + \frac{1}{60+2} = 0.01639 + 0.01612$ | **0.03251** | **Rank 1** |
| **Doc B** | 2 | 1 | $\frac{1}{60+2} + \frac{1}{60+1} = 0.01612 + 0.01639$ | **0.03251** | **Rank 2** (tie-break) |
| **Doc C** | 15 | 3 | $\frac{1}{60+15} + \frac{1}{60+3} = 0.01333 + 0.01587$ | **0.02920** | **Rank 3** |
| **Doc D** | 3 | 50 | $\frac{1}{60+3} + \frac{1}{60+50} = 0.01587 + 0.00909$ | **0.02496** | **Rank 4** |

---

## 4. Hard Reviewer Defenses on RRF

#### Q: Why not simply concatenate search results?
* **Student Answer:** "Concatenation appends results without re-ordering. If BM25 returns 10 items and Dense returns 10 items, concatenation puts all BM25 items first, ignoring high-quality vector matches."

#### Q: Why not take the max score from either retriever?
* **Student Answer:** "Raw BM25 scores (e.g., 15.2) and vector distances (e.g., 0.82) are on completely unnormalized scales. Taking max scores creates extreme scale bias toward whichever retriever outputs higher numerical ranges."

#### Q: What happens if retrievers disagree completely?
* **Student Answer:** "RRF assigns equal reciprocal rank weight to both. A document ranked 1st in BM25 and unranked in Dense gets $\frac{1}{61} = 0.01639$, placing it safely in the middle of the fused top-20 candidate pool."

# PART H — BGE CROSS-ENCODER RERANKING (`BAAI/bge-reranker-base`)

## 1. Bi-Encoder vs Cross-Encoder Mechanics

```
BI-ENCODER (First-Stage Retrieval):
  Query ────► [Transformer Encoder] ────► Vector Q ──┐
                                                     ├──► Dot Product / Cosine (Sub-15ms)
  Snippet ──► [Transformer Encoder] ────► Vector D ──┘

CROSS-ENCODER (Second-Stage Reranking):
  (Query + Snippet) ────► [Joint Cross-Attention Transformer] ────► Relevance Score S ∈ [0, 1] (42ms)
```

| Dimension | Bi-Encoder (`bge-base-en-v1.5`) | Cross-Encoder (`bge-reranker-base`) |
| :--- | :--- | :--- |
| **Processing** | Encodes Query and Snippet separately into vectors | Encodes Query and Snippet *together* in concatenated string |
| **Attention** | Self-attention within query tokens and document tokens independently | **Full Cross-Attention** between every query token and document token |
| **Indexing** | Vectors can be pre-computed and stored in ChromaDB | Cannot be pre-computed (requires active query string at runtime) |
| **Speed** | Extremely fast (P50 = 12.5 ms over 14,850 items) | Slower (P50 = 42.5 ms over 20 items) |
| **Accuracy** | High overall semantic recall | **Exceptional top-1 precision** (captures fine word interaction) |

---

## 2. Why We Cannot Use Cross-Encoders on the Entire Corpus
`[General Technical Explanation]` A cross-encoder takes ~2 ms per pair. Running a cross-encoder across all 14,850 chunks in our local database would take $14,850 \times 2\text{ms} \approx 29.7\text{ seconds}$ per query. Using a bi-encoder first reduces 14,850 candidates to 20 in 18 ms, allowing the cross-encoder to run on 20 candidate pairs in 42.5 ms.

---

## 3. Reranking Data Structures & Metadata Fields
`[Project Fact]` The system tracks four explicit rank fields in pipeline execution logs:
* `pre_rerank_rank`: Document rank position resulting from initial RRF hybrid fusion (1 to 20).
* `post_rerank_rank`: Document rank position after BGE cross-encoder evaluation (1 to 5).
* `bge_score`: Scalar relevance output $S_{\text{rerank}} \in [0, 1]$ produced by `bge-reranker-base`.
* `rank_delta`: $\Delta r = \text{pre\_rerank\_rank} - \text{post\_rerank\_rank}$. Positive delta indicates rank improvement.

# PART J & K — ENHANCED RAG & GEMINI 2.5 FLASH

```
[Reranked Top-5 Snippets] ──► [Phase 3.3 Enhanced RAG] ──► [Context-Bound Prompt] ──► [Gemini 2.5 Flash] ──► [Cited Draft]
```

### 1. What is RAG?
* **Simple English:** Giving an AI an "open book" containing verified text snippets before asking it to write an answer.
* **Technical Explanation:** `[General Technical Explanation]` Retrieval-Augmented Generation condition the probability of generating token sequence $Y$ on query $X$ and retrieved document context $Z$:
  $$P(Y|X) = \prod_{i=1}^{n} P(y_i \mid X, Z, y_1, \dots, y_{i-1})$$

---

### 2. Phase 3.3 Enhanced RAG Features
`[Project Fact]` Standard RAG allows LLMs to blend context with pre-trained parametric memory. Enhanced RAG introduces:
1. **Context Eligibility Validation:** Checks if retrieved snippet similarity score exceeds threshold $0.45$.
2. **Evidence Deduplication:** Strips redundant duplicate text across chunks.
3. **Structured Context Bounding:** Wraps snippets inside isolated tags (`[Chunk 1]`, `[Chunk 2]`).
4. **Strict Negative Constraints:** Prompts: *"Answer ONLY using provided chunks. Forbid parametric memory use. If context is insufficient, state Insufficient Evidence."*

---

### 3. Role of Gemini 2.5 Flash
* **Input:** Context-bound system prompt + 5 reranked snippets + Query.
* **Settings:** `temperature = 0.0` (deterministic), `max_output_tokens = 1024`.
* **Output:** Formatted scientific answer with inline citation tags (`[1]`, `[2]`).
* **Why an LLM is needed after retrieval:** Retrieved passages are raw unorganized snippets. The LLM acts as a synthesizer, organizing snippets into coherent, readable paragraphs while maintaining exact citations.

### 1. Stage A: Structural Parsing & Claim Extraction
* **Method:** Deterministic regex parsing isolates sentences and maps attached citation keys.
* **Output:** Claim objects containing claim text, cited chunk ID, and sentence index.

### 2. Stage B: Gemini NLI Entailment Classification
* **Prompt:** *"Evaluate if Evidence Chunk strictly ENTAILS Claim Sentence. Output ENTAILES, NEUTRAL, or CONTRADICTS."*
* **Entailment Classifications:**
  - `ENTAILES`: Claim is fully supported by snippet.
  - `NEUTRAL`: Snippet discusses topic but lacks specific claim facts.
  - `CONTRADICTS`: Snippet directly contradicts claim.

### 3. Claim & Citation Status Definitions

| Status Type | Value | Meaning |
| :--- | :--- | :--- |
| **Claim Status** | `SUPPORTED` | Claim sentence is logically entailed by cited snippet. |
| **Claim Status** | `PARTIALLY_SUPPORTED` | Snippet supports part of claim but lacks quantitative specifics. |
| **Claim Status** | `UNSUPPORTED` | No snippet in corpus supports the claim. |
| **Citation Status** | `VALID` | Inline citation tag `[1]` points to an entailing snippet. |
| **Citation Status** | `INVALID` | Inline citation tag `[1]` points to a non-entailing snippet. |
| **Citation Status** | `REPAIRED` | Invalid tag `[1]` was re-linked to entailing snippet `[4]`. |

# PART N — ITERATIVE REFINEMENT ENGINE (PHASE 3.5)

### 1. Self-Feedback Gap Taxonomy
`[Project Fact]` The Phase 3.5 Refinement Engine evaluates draft answers against 6 feedback classes:
1. `MISSING_EVIDENCE`: Key sub-question unaddressed by retrieved context.
2. `WEAK_EVIDENCE`: Retrieved context provides low-confidence support.
3. `UNSUPPORTED_CLAIM`: Answer draft contains unverified claims.
4. `PARTIAL_SUPPORT`: Context partially answers query.
5. `NUMERICAL_SUPPORT_GAP`: Quantitative statistic lacks exact snippet grounding.
6. `NO_REFINEMENT_NEEDED`: Answer satisfies all precision and evidence criteria.

---

### 2. Refinement Loop Execution
If gaps exist and cycle count $< 2$:
1. Generates targeted sub-query $Q_{\text{sub}}$.
2. Executes re-retrieval across local KB / dynamic APIs.
3. Merges new snippets into evidence manifest.
4. Re-synthesizes final grounded answer.

*Why limit to 2 cycles?* Iterative refinement is hard-capped at max 2 cycles to prevent infinite LLM loops and control latency overhead (E05 P50 latency = 1253.3 ms).

# FINAL SECTION — THE COMPLETE INTERNAL WORKFLOW EXPLAINED FOR AN AI EXPERT

> **Reviewer Prompt:** *"When a researcher asks one question, show me everything that happens inside ResearchMind until the final verified answer is produced."*

### Step 1: Query Reception & Normalization
* **Request:** User submits query string $Q$: *"How do graph-based agent architectures improve tool selection?"* via React frontend UI.
* **FastAPI Handler:** `/api/search` receives JSON payload. Pydantic validates input types. Query is lowercased and stripped of control characters.

### Step 2: Parallel Dual Retrieval Execution
* **BM25 Inverted Index:** Tokenizes $Q$ into terms $\{t_1, \dots, t_n\}$. Computes $\text{Score}_{\text{BM25}}(D, Q)$ across 14,850 local KB chunks, outputting ranked list $R_{\text{sparse}}$ (Paper A @ Rank 1, Paper C @ Rank 2, Paper B @ Rank 12).
* **Dense Vector Index:** Passes $Q$ to `BAAI/bge-base-en-v1.5`, generating embedding $\vec{v}_q \in \mathbb{R}^{768}$. ChromaDB executes HNSW L2 distance search over 14,850 vectors, outputting ranked list $R_{\text{dense}}$ (Paper B @ Rank 1, Paper D @ Rank 2, Paper A @ Rank 3).

### Step 3: Reciprocal Rank Fusion (RRF $k=60$)
* For each candidate document $d$, computes unified fusion score:
  $$S_{\text{RRF}}(d) = \frac{1}{60 + r_{\text{sparse}}(d)} + \frac{1}{60 + r_{\text{dense}}(d)}$$
* $S_{\text{RRF}}(\text{Paper A}) = \frac{1}{61} + \frac{1}{63} = 0.03226$. $S_{\text{RRF}}(\text{Paper B}) = \frac{1}{72} + \frac{1}{61} = 0.03028$.
* Returns top-20 merged candidate pool $R_{\text{hybrid}}$ (Paper A @ Rank 1, Paper B @ Rank 2).

### Step 4: Cross-Encoder Reranking
* Concatenates query with top-20 candidate snippets into sequence `"[CLS] Q [SEP] Snippet_i [SEP]"`.
* Passes pairs through `BAAI/bge-reranker-base` cross-attention transformer layers.
* Cross-encoder evaluates token-level interactions: Paper B BGE Score = 0.964 (Elevated to Rank 1); Paper A BGE Score = 0.880 (Rank 2); Paper C (distractor) BGE Score = 0.120 (Dropped to Rank 14).
* Returns top-5 reranked context snippets.

### Step 5: Phase 3.3 Enhanced RAG Prompt Assembly
* Deduplicates snippets and checks similarity thresholds ($>0.45$).
* Wraps snippets inside isolated context blocks: `[Chunk 1]`, `[Chunk 2]`.
* Injects strict negative constraints: *"Answer ONLY using provided text blocks. Forbid parametric memory use. Include bracketed citations [1], [2]."*
* Passes prompt to Gemini 2.5 Flash (`temp=0.0`).

### Step 6: Generative Synthesis
* Gemini 2.5 Flash generates draft response: *"Graph agent architectures structure tool selection as decision node routing [1], reducing search space by 35% [1]."*

### Step 7: Phase 3.4 Claim Verification & Citation Repair
* **Stage A:** Regex parses sentence $S_1$: *"Graph agent architectures structure tool selection as decision node routing [1]"* and sentence $S_2$: *"reducing search space by 35% [1]"*.
* **Stage B:** Gemini NLI evaluates: Does Chunk 1 entail $S_2$? Output = `NEUTRAL` (Chunk 1 discusses routing, not 35% reduction). Tag `[1]` on $S_2$ is tagged `INVALID`.
* **Citation Repair:** Engine scans remaining top snippets, finds Chunk 4 contains "35% reduction". Updates $S_2$ citation to `[4]`. Citation Status = `REPAIRED`.

### Step 8: Phase 3.5 Refinement & Final Response Render
* Refinement Engine checks feedback: `NO_REFINEMENT_NEEDED`. Refinement cycle terminates (Cycle 1).
* FastAPI returns final payload containing verified text, clickable inline citation links, and raw XAI trace metrics. React UI renders grounded answer with green `100% VERIFIED` badge.
